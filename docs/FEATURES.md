# Features

The full tour. The [README](../README.md) has the short version.

- **Pixel office** -- Canvas-rendered workstations that show each agent's state at a glance (working, waiting, needs attention, idle, disconnected). Desks are grouped into per-repo pods, each on its own labeled rug, in a front-facing grid (up to four desks across, wrapping into rows with an aisle between); a sparse office shows a row of empty spare desks below the real one, a conference table with cushioned chairs sits in the open floor below them, and the bottom of the floor fills with ambient decor (a sofas-and-coffee-table chat area in each corner, the two plants stacked between them as a divider) that yields as the office gets crowded; low bookshelves run under the windows. Pixel-art characters (six sprite variants) face the screen when working, turn to face you when waiting, and wander off to sit down when they are at rest -- at the conference table when the window is tall enough for one, and otherwise on the corner sofas, which are there at any size. A newly spawned agent walks in from the entrance to its desk, a departing one walks out before its desk disappears, and when the job board dispatches a job a small paper flies from that job's whiteboard column to the new agent's desk (all motion respects `prefers-reduced-motion`). The three whiteboards mirror the job board live: one pinned paper per job in each column, with a "+N" note when more are queued than fit -- click one to open the Jobs tab.
- **Git worktree isolation** -- Each agent gets its own worktree and branch automatically. No merge conflicts between agents working on the same repo. Branches are named with cocktail names (`bill/vesper`, `bill/martini`, ...).
- **Multi-repo support** -- Add any number of repos. Spawn agents on different repos and manage them all from one place.
- **Live file explorer** -- Real-time file tree with git status indicators, inline diff viewer, and a changes/all toggle to filter what you see. Repo sections collapse from their header (click, or Enter/Space when focused); a collapsed header keeps the agent count and a dot for the most urgent agent state, so folded sections still show when something needs you.
- **Terminal multiplexer** -- Full xterm.js terminals with clickable URLs, clipboard image paste (Cmd+V a screenshot), and draggable tabs for reordering. Double-click an agent's tab (or press the pencil button in the terminal header) to rename it; the new name shows up in every panel and in every connected browser, and survives a server restart. Only the label changes -- the agent's worktree directory and branch keep their original codename, so nothing moves under a running session. Open the same terminal in several windows (a laptop and a phone, or you and a teammate watching) and it takes the size of the smallest of its owner's windows showing it, as tmux does: every window draws it at that size, so a bigger one shows some empty space instead of scrambled lines.
- **Job board** -- Queue work instead of babysitting it. A job has a title, details, and a repo, plus any screenshots or files you attach (paste an image into Details, or **Attach files**); they are stored outside the repo and the agent is told where to read them (it reads whatever you attach, so treat a file from outside the way you would treat pasted instructions). The board scans every 5 minutes, and for each queued job whose repo is under its agent cap it spawns a fresh agent on its own worktree and a branch named after the job. When the agent is done it reports back to the board with the pull request it opened (the board also spots the PR on its own if the agent forgets). Set **Pull request: Not required** on a card for work that is not a code change, such as research or a chore: its agent is not told to ship, reports a summary instead, and the summary shows on the card in Review. Agents dispatch in `auto` mode, where Claude Code's classifier reviews each action and escalates the rest to you -- worth having, because a job agent's prompt is your card text plus whatever it reads out of the repo. Set **permissions** in the board toolbar to change that for every job, or **Permissions** on a card to change it for one; a card left on "Board default" follows the board setting, including if you change it later. **Agent** on a card picks the CLI it runs on, Claude Code or Codex; Codex has no permission modes of its own, so a Codex card offers board default, `auto` (Codex's own default: it writes in the worktree and asks before risky commands) and `bypassPermissions` (`--dangerously-bypass-approvals-and-sandbox`). A board set to another mode maps onto Codex's nearest flag, so a strict board binds a Codex card too: `plan` runs it read-only, `manual` keeps it read-only and turns every write into a question, `dontAsk` never asks and fails instead, and `acceptEdits` is Codex's default. Auto mode needs a classifier that isn't available everywhere (an unsupported model on Bedrock or Vertex, or a machine with `permissions.disableAutoMode` set), and where it's missing Claude Code quietly starts the agent in manual instead -- so every job runs until it needs your permission and then waits there, showing orange on the card. That is what the board setting is for. In `bypassPermissions` a job agent edits files and runs Bash unprompted as you, and nothing inside the app bounds it, so only queue jobs against repos whose contents you trust ([DESIGN.md](../DESIGN.md) has the reasoning). Jobs move To do -> In progress -> Review on their own. A card in Review keeps its agent running, so you can click it to open that terminal and ask about the work; the agent and its worktree are released when the card reaches Done or goes back to To do, and agents waiting in Review do not count toward the cap. Once the pull request merges, or you mark the card done, it leaves the board for **View finished jobs** -- so the Review column keeps meaning "needs your review". A finished card stays finished: it is the record of what shipped, and follow-up work is a new job. An agent that stops to ask you something turns its card orange and puts a count on the Jobs tab; click it to land in that terminal, answer, and it carries on.
- **Scheduled jobs** -- A card can also be a standing one, fired by a cron schedule (`0 9 * * 1-5`, or `@daily`) in the server's local time rather than dispatched once. A scheduled job need not be a coding task -- it does the work, writes what it found in its terminal, and when it goes quiet the board puts the card back in To do with its next run time, keeping the terminal open to read until the next run replaces it. That next run also clears away the last run's worktree, any files it left behind included; only commits that were never pushed keep it around as an orphan. It cycles To do -> In progress -> To do, never reaches Review, and sits outside the per-repo agent cap, so busy one-time jobs can't starve a schedule. **Pause** on the card holds every further run without deleting it -- during a run as well as between runs, where **End run** stops the run that is going and Pause stops the ones after it; **Resume** sets the next run from that moment, so a card paused for a week doesn't fire the instant it comes back.
- **Ask an agent to post a job** -- Say "add that to the job board" to an agent you are already working with and it posts the card itself, so noticing work does not mean stopping to type it into the form. The board appears in every Claude Code and Codex agent as an MCP tool, so the agent can see it without being told it exists; under the default permission mode Claude Code still asks you to approve the call, so a card is never filed behind your back. A card an agent files always inherits the board's permission mode -- an agent cannot pick the mode the board will spawn with. It runs on the same CLI as the agent that filed it unless the agent names another; a card a person files runs on Claude Code unless they pick Codex. The card lands in To do showing "via <agent>", and runs in that terminal's repo unless the agent names another. The same agent can read the board back to you and change a card you have not started yet -- "what is queued?", "what does that card say?", "add the repro steps to it". A card that has left To do is closed to edits, for you and for it alike, because its agent already has the text; an agent cannot touch a card someone else queued; and an edit that does land is announced and shown on the card, so a rewritten card never reads as the work of whoever queued it.
- **Agents message each other** -- Say "ask Viper what it changed in jobs.js" and the agent sends the question itself, whether Viper runs on Claude Code or Codex. Every agent has two MCP tools for this, `list_agents` and `send_message`, on the same server as the job board. Claude Code's own messaging only reaches other Claude Code sessions. A message is typed into the other agent's terminal as a new turn, headed with who sent it, so you see it arrive and the agent answers it like anything else you typed. It is typed in only while that agent rests at its prompt: never while it is working, never into a permission or trust dialog the app recognises (the Enter would answer it), and not within 30 seconds of you typing in that terminal. "Rests at its prompt" means no recognised dialog is on screen, so a dialog a new CLI release words differently could still be answered by the Enter. Until then it waits in a queue of up to 20. The reply comes back the same way. An agent reaches only agents with the same owner, never a plain shell tab, and one agent can send another at most 10 messages in 10 minutes, so two agents cannot keep answering each other for ever. An agent that never asks before acting (`bypassPermissions`, `--dangerously-skip-permissions`, or on Codex `--yolo`, `danger-full-access`, `--ask-for-approval never`, `--full-auto`, or any `-c`/`--profile` override) only takes messages from another agent that never asks: otherwise any agent could borrow its permissions just by asking it to do something. This is read off the command line the agent was started with, so a bare `claude` or `codex` whose own config file turns the questions off is not caught by it. A message is a prompt, and it runs with the recipient's permissions, not the sender's: an agent in `bypassPermissions` acts on what it is sent as it would on what you type. The header says the message came from an agent, and the body is quoted line by line so it cannot pass itself off as you. That helps, but it is not a sandbox.
- **An orchestrator agent** -- Messaging plus the job board are enough for one agent to run the others. Give it its own repo, a charter, and a self-paced `/loop`: each cycle it reads its notes, checks every agent, gives each waiting one its next task, posts jobs for work nobody owns, and logs what it decided. Its memory is files in its own repo, so it picks up where it left off after a restart. [`templates/orchestrator/`](../templates/orchestrator/) is a charter to start from; it decides on its own except for money, missing access, and irreversible or public steps, which it brings to you. It works only if it and the agents it manages run in the same kind of permission mode, because an agent that never asks takes messages only from another that never asks. It cannot restart agents or answer their permission dialogs. [ORCHESTRATOR.md](ORCHESTRATOR.md) has the setup and the limits.
- **Works on a phone** -- Below 700px the three panels become one screen at a time, switched from a Files / Office / Terminal bar at the bottom. Tapping a desk or whiteboard in the office lands you in that terminal or the job board, and opening a file diff lands you in the office panel, the same as on a desktop.
- **Dark/light themes** -- Gold-accented dark theme and a warm low-glare paper light theme tuned for long sessions (see [DESIGN.md](../DESIGN.md)). Toggles instantly, terminal colors and office canvas included.
- **Live sync** -- Branch names, file changes, line-level diff stats (+/-), and agent states update in real time across all panels.
- **Voice input** -- Dictate prompts instead of typing. Click the mic button floating at the terminal's bottom-right (or `Cmd+D`), allow microphone access on first use, speak, and the transcript is typed into the active terminal; press Enter to send. Uses the browser's Web Speech API (Chrome, Edge, Safari; the recognition language follows your browser's locale) and needs HTTPS or localhost -- for remote access use `tailscale serve` (see [REMOTE.md](REMOTE.md)). The mic is deliberately bounded: it stops after ~1 minute without delivered speech, always after 5 minutes, on switching or closing agents, when an agent's shell ends, when the tab is hidden, and on a phone when you leave the terminal panel. Two things to know: most browsers process speech on vendor servers (Chrome/Edge send audio to Google/Microsoft; Safari may process on-device), so don't dictate secrets; and transcripts arrive as keystrokes, so a program waiting on a single key (a pager, a y/n prompt) reacts to speech like typing -- watch the prompt while dictating. OS-level dictation (macOS dictation, iOS keyboard mic, Windows `Win+H`) also types straight into the terminal and works in any browser.
