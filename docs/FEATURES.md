# Features

The full tour. Agent 007 grows with how much you hand off: web terminals for your coding agents, many of them in one window, a job board they pick work from, and Billion, one agent that runs the board from a goal. The [README](../README.md) has the short version.

- **Billion, the one agent you talk to** -- The server starts an always-on Claude Code agent called Billion. You give it a mission, narrow ("ship the Windows build") or broad ("grow the company"), and it runs the work: it plans, posts job cards, reviews what comes back, merges pull requests, and comes to you only for money, access, anything irreversible, making a private repo public, payments or security, and real forks in direction. It runs without permission prompts (`--dangerously-skip-permissions`), so those rules are its brakes. On its first start it introduces itself, shows you what it will always ask you about, and asks for your mission and where new project repos should go; after that the server wakes it for each operating cycle, paced by Billion with `set_next_wake`, and a server restart resumes its last conversation (`claude --continue`, or its Codex session by id). Its memory is a git repo of its own in `~/.agent-007/billion`: your rules in `CLAUDE.md`, the mission and what it learns in `COMPANY.md`, its current plan in `STATE.md`, every change a commit. Its instructions (`CHARTER.md`) are Agent 007's and are rewritten on every start, so a new release reaches it without touching your rules. It sits pinned at the top of the left panel and alone at the top of the office, and its terminal runs from the start, its tab hidden until you click Billion in the office (or its row); closing that tab hides it again and never stops Billion. Nothing restarts it on its own: a stopped Billion shows a Start button. If Claude Code is not installed, Billion's tab says so, with where to get it; install it and press Start, or set `BILLION=0`. Every agent can message Billion, whoever owns it, and messages and board notices wait until Billion says it is ready, so nothing lands mid-introduction. A card Billion posted tells it the moment it reaches Review, with the pull request or summary, and again once CI on that pull request finishes on its latest commit (all passed, or which checks failed), so Billion merges on that instead of watching CI itself; only Billion can edit its cards, and it can accept one that has no pull request or send it back to To do with a note for the next worker. It can also add a new project's repo to the board, and read the last lines of a worker's terminal on one of its own cards (`read_agent_screen`) to see why it stalled; agents you start by hand stay off-limits. A worker on one of Billion's cards, Claude Code or Codex, asks Billion before it asks you: Billion allows, denies with a reason the worker reads, or leaves it to you, and anything it does not answer within two minutes comes to you as the usual dialog. A request it could not see in full, a question or plan approval, or text that tries to steer its answer always reaches you instead, and a server that is down or slow never approves anything. A Codex worker gets its hook as two `-c` flags for that run, the hook and its trusted hash, so nothing is written to `~/.codex/config.toml`; the server asks Codex for that hash when it starts (`codex app-server`, `hooks/list`), and if `codex` is missing or does not answer, Codex workers ask you as before. If you have a `PermissionRequest` hook of your own in `~/.codex/hooks.json`, both run: a deny from either wins, then an allow from either, and only when neither decides do you see the dialog. Workers on either CLI call `send_message` and `finish_job`, the two board tools every worker on Billion's card is told to use, without a dialog (for Codex, `-c mcp_servers.agent-007-board.tools.<tool>.approval_mode="approve"` for that run only); any other board tool still asks. It runs on Claude Code, or on Codex with `BILLION_AGENT=codex`; the button next to its name switches between them, handing the end of the conversation over in `HANDOVER.md`; the server does the same by itself when the one it runs on hits its usage limit, and never switches back on a timer (`BILLION_AUTO_SWITCH=0` turns that off); and on both the server wakes it for each operating cycle ([BILLION.md](BILLION.md#claude-code-or-codex)). `BILLION=0` turns it off and `BILLION_DIR` moves its folder (it must be new or empty). It stays off while user accounts are enabled, since it would belong to everyone. One thing to know: a worker that read untrusted text can pass it on to Billion, which has full access; messages arrive labelled as coming from an agent and its charter treats them as information, not instructions, but that is not a sandbox. The design, step by step, is in [BILLION.md](BILLION.md).
- **Talk to Billion in the Billion tab** -- The Billion tab is a chat thread with Billion, and the tab a page opens on (it cannot be closed), the web twin of its Telegram channel, so the conversation is not buried under the board notices and worker messages in its terminal (which stays the work log). Type in the box at the bottom (Enter sends) and it reaches Billion as `[Owner via app] ...`; Billion's `tell_owner` replies and questions show as bubbles on the left, your messages on the right, Telegram ones included (voice notes as their transcript, marked *(voice)*). Typing is always a plain message: to answer a question by typing, tap *Reply* under it (or its chip in the strip) and the box says "Answers Q3". *Undo* takes an answer back for a minute after, and Billion can reopen a question with `reopen_question`. Open questions also pin to a strip at the top. The last 500 messages are kept in `~/.agent-007/chat.json`.
- **Read aloud and dictate in the Billion tab** -- A speaker button on every message from Billion reads it aloud with the browser's own voices (free, nothing leaves the browser): markdown dropped, links read as "link", Q51 as "question 51", a question's choices at the end, long messages spoken sentence by sentence; tap again to stop, and pick the voice at the top of the tab. Turn on *Read new messages aloud* at the top of the tab and each new message is spoken as it arrives while the tab is showing (after a reload, one tap on *Resume reading*). The mic beside the text box dictates a reply into the box, greyed while it is heard, and never sends it for you; in "Answers Q3" mode it answers Q3 like typed text. Locked-screen playback on a phone is not reliable in mobile browsers; Telegram voice notes cover that. See [BILLION.md](BILLION.md#read-aloud-and-dictation-in-the-tab).
- **Billion asks you on your phone** -- When Billion needs you, its `notify_owner` tool puts the question, numbered (Q3), in the **Billion** tab next to Jobs (a chat bubble and "Billion", with a badge counting open questions; the same in a phone's bottom bar) and, with `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` set, sends it to you through a Telegram bot. A question can carry 2 to 5 `choices` with one `recommended`: tap one under the question in the tab or its Telegram button, or type an answer in the tab's text box or as a Telegram reply to the question. It reaches Billion as `[Owner via app] Q3: ...` or `[Owner via Telegram] Q3: ...`, and the question is marked answered in both places (the Telegram message is edited to show the answer). Each question carries an `urgency`: open ones list **blocking** first (marked `! Q3`: a worker or merge is waiting, and the Telegram message starts with `! `), then normal, then **low** (number dimmed: optional), oldest first within each. Answered ones stay in the thread with "you answered: ..."; *Dismiss* closes one; everything survives restarts. Anything else you send the bot is typed into Billion's terminal as `[Owner via Telegram] ...`. Telegram buzzes for every question, but Billion's `tell_owner` replies reach it only while you are talking on the phone: after a message from the tab they stay in the tab ([details](BILLION.md#telegram)). The bot is Billion's own, so its messages carry no name: `Q3: ...`, `! Q3: ...`, or a reply's text alone. Only your chat is accepted. Setup in three steps is in [BILLION.md](BILLION.md#telegram). **Voice both ways, all local**: on macOS with ffmpeg, Billion's messages can arrive as voice notes (spoken by `say`, with the text as caption), and your voice notes are transcribed on your machine by whisper.cpp and reach Billion as `[Owner via Telegram, voice] ...`. By default Billion answers in the mode you last used (`TELEGRAM_VOICE`); see [Voice](BILLION.md#voice).
- **Claude account, moved in place** -- For a permanent move from one Claude subscription to another. The default Claude Code setup (`~/.claude`, `~/.claude.json`: conversations, settings, skills, plugins, MCP servers, trusted folders) stays exactly as it is and only the login changes, so Billion resumes its conversation on the new account and nothing has to be set up again. Log the new account in once in a folder of its own (`CLAUDE_CONFIG_DIR=~/.claude-new claude`, then `/login`), then open the Settings gear in the terminal header, find **Claude account**, give that folder and press **Check folder**: the app confirms the folder is logged in (`claude auth status --json`) and shows both emails. Nothing is armed and nothing happens until you press one of the buttons, each behind a confirm: **Switch now** does it at once; **Arm** does it the first time Claude Code prints a hard usage-limit notice on Billion's screen (the same notice that would otherwise switch Billion to Codex; while armed, the account switch comes first and Billion stays on Claude Code, and only if it fails does the Codex switch follow), then disarms; **Disarm** takes it back. Nothing in the board reaches it: there is no tool for it, the WebSocket message that carries it is accepted only from this server's own page (a socket without an Origin, or with another site's, is refused), and with user accounts on nobody can, the armed switch included. That is friction, not a sandbox: a process running as you, an agent in `bypassPermissions` included, can forge an Origin or read the Keychain directly without this server; Billion's charter forbids it, as it forbids everything else it could do as you. Once armed, the moment of the switch is whatever prints a limit notice on Billion's screen. A switch backs up the current login first (the Keychain item's secret and the account block of `~/.claude.json`, 0600 files under `~/.agent-007/account-backup/<time>/`, never written to the log), writes the new folder's token into the default Keychain item (`add-generic-password -U` on `/usr/bin/security`'s stdin, so the token is never on a command line; the item and account attribute are the ones Claude Code itself uses, and the token is read back to check it landed; on Linux it copies `.credentials.json` at 0600) and the new folder's account block into `~/.claude.json` (under Claude Code's own `.claude.json.lock`, a temp file renamed over it, retried if the file changes meanwhile, everything else in the file kept), then checks that `claude auth status --json` reports the new email. If it does not, the backup goes straight back, that restore is checked the same way, and the panel says so; a write that failed before anything moved needs no restore and just reports; a restore that fails too shows as such and offers Roll back and Check folder. One action runs at a time, across server processes too. Neither check exercises the token against Anthropic (`claude auth status` reads what is on disk), which is why you validate before retiring. Forty seconds after a switch the login is looked at once more, since a running Claude Code that refreshed its token in between could have written the old account's back; if so you are told and the panel says so. Backups are kept until you delete them; each holds a login's token at 0600. Billion restarts on the new login; running workers are left alone, since Claude Code re-reads its token every 30 seconds. **Roll back** restores the backup the switch made and checks the old email again; the login it replaces is backed up first, so a rollback never destroys the only copy of a working login. The new folder is not touched, so it stays a fallback, but after the switch its token and the default one are the same login: never run anything with `CLAUDE_CONFIG_DIR` pointing at it, or a token refresh there can log the default out. Validate first (Billion working on the new account, a `claude` started by hand shows the new email in `/status`, a day of normal use), then **Retire the new folder** renames it to `<folder>.retired-<date>`; nothing here ever deletes it. You are told in the Billion tab, and on Telegram unless your last message came from the tab (otherwise in a browser notice), on success, failure and rollback, with the emails and the result only. This is not for rotating accounts to get past a usage limit; Anthropic's terms are yours to keep.
- **Pixel office** -- Canvas-rendered workstations that show each agent's state at a glance (working, waiting, needs attention, idle, disconnected). Desks are grouped into per-repo pods, each on its own labeled rug, in a front-facing grid (up to four desks across, wrapping into rows with an aisle between); a sparse office shows a row of empty spare desks below the real one, a conference table with cushioned chairs sits in the open floor below them, and the bottom of the floor fills with ambient decor (a sofas-and-coffee-table chat area in each corner, the two plants stacked between them as a divider) that yields as the office gets crowded; low bookshelves run under the windows. Pixel-art characters (six sprite variants) face the screen when working, turn to face you when waiting, and wander off to sit down when they are at rest -- at the conference table when the window is tall enough for one, and otherwise on the corner sofas, which are there at any size. A newly spawned agent walks in from the entrance to its desk, a departing one walks out before its desk disappears, and when the job board dispatches a job a small paper flies from that job's whiteboard column to the new agent's desk (all motion respects `prefers-reduced-motion`). The three whiteboards mirror the job board live: one pinned paper per job in each column, with a "+N" note when more are queued than fit -- click one to open the Jobs tab.
- **Git worktree isolation** -- Each agent gets its own worktree and branch automatically. No merge conflicts between agents working on the same repo. Branches are named with cocktail names (`bill/vesper`, `bill/martini`, ...).
- **Multi-repo support** -- Add any number of repos. Spawn agents on different repos and manage them all from one place.
- **Live file explorer** -- Real-time file tree with git status indicators, inline diff viewer, and a changes/all toggle to filter what you see. Repo sections collapse from their header (click, or Enter/Space when focused); a collapsed header keeps the agent count and a dot for the most urgent agent state, so folded sections still show when something needs you.
- **Terminal multiplexer** -- Full xterm.js terminals with clickable URLs, clipboard image paste (Cmd+V a screenshot), and draggable tabs for reordering. Double-click an agent's tab (or press the pencil button in the terminal header) to rename it; the new name shows up in every panel and in every connected browser, and survives a server restart. Only the label changes -- the agent's worktree directory and branch keep their original codename, so nothing moves under a running session. Open the same terminal in several windows (a laptop and a phone, or you and a teammate watching) and it takes the size of the smallest of its owner's windows showing it, as tmux does: every window draws it at that size, so a bigger one shows some empty space instead of scrambled lines.
- **Job board** -- Queue work instead of babysitting it. A job has a title, details, and a repo, plus any screenshots or files you attach (paste an image into Details, or **Attach files**); they are stored outside the repo and the agent is told where to read them (it reads whatever you attach, so treat a file from outside the way you would treat pasted instructions). While the board is running, a queued job whose repo is under its agent cap gets a fresh agent on its own worktree and a branch named after the job within a couple of seconds: posting a card, moving one back to To do, or a worker's slot freeing up (its card to Review or Done, or its agent gone) each start a dispatch pass. A card that comes back to To do (moved there by hand, or sent back by Billion) is held for a minute first, showing "held · dispatching in Ns", so it can be edited before a new worker picks it up; editing does not lift the hold, **Dispatch now** on the card does. The board also scans every 5 minutes as a fallback, which is when it finds pull requests and files merged cards; **Run now** does that scan on demand. When the agent is done it reports back to the board with the pull request it opened (the board also spots the PR on its own if the agent forgets). Set **Pull request: Not required** on a card for work that is not a code change, such as research or a chore: its agent is not told to ship, reports a summary instead, and the summary shows on the card in Review. Agents dispatch in `auto` mode, where Claude Code's classifier reviews each action and escalates the rest to you -- worth having, because a job agent's prompt is your card text plus whatever it reads out of the repo. `CLAUDE_PERMISSION_MODE` / `CODEX_PERMISSION_MODE` in `.env` set another default per CLI, which the toolbar shows as ".env: …" until a mode is picked there; a picked mode overrides both. Set **permissions** in the board toolbar to change that for every job, or **Permissions** on a card to change it for one; a card left on "Board default" follows the board setting, including if you change it later. **Model** on a card picks the model its CLI runs (`--model` for Claude Code, `-m` for Codex), shown on the card; left on "CLI default" the CLI chooses. The list is discovered, never typed in: Claude Code's aliases for its newest models (`fable`, `opus`, `sonnet`, `haiku`) when `claude` is installed, and the models Codex lists in its picker (from `codex debug models`, or `$CODEX_HOME/models_cache.json` if that command fails, which the board only reads; hidden internal ones such as `codex-auto-review` are left out) when `codex` is. It is found at startup, again every hour and when the card form opens on a list over 10 minutes old; a value not on the list is refused, and a worker re-spawned after a restart keeps its card's model. Agents choose one with `post_job` / `edit_job`, whose description lists what is available. **Agent** on a card picks the CLI it runs on, Claude Code or Codex; Codex has no permission modes of its own, so a Codex card offers board default, `auto` (Codex's own default: it writes in the worktree and asks before risky commands) and `bypassPermissions` (`--dangerously-bypass-approvals-and-sandbox`). A board set to another mode maps onto Codex's nearest flag, so a strict board binds a Codex card too: `plan` runs it read-only, `manual` keeps it read-only and turns every write into a question, `dontAsk` never asks and fails instead, and `acceptEdits` is Codex's default. Auto mode needs a classifier that isn't available everywhere (an unsupported model on Bedrock or Vertex, or a machine with `permissions.disableAutoMode` set), and where it's missing Claude Code quietly starts the agent in manual instead -- so every job runs until it needs your permission and then waits there, showing orange on the card. That is what the board setting is for. In `bypassPermissions` a job agent edits files and runs Bash unprompted as you, and nothing inside the app bounds it, so only queue jobs against repos whose contents you trust ([DESIGN.md](../DESIGN.md) has the reasoning). Jobs move To do -> In progress -> Review on their own. A card in Review keeps its agent running, so you can click it to open that terminal and ask about the work; the agent and its worktree are released when the card reaches Done or goes back to To do, and agents waiting in Review do not count toward the cap. Once the pull request merges or is closed without merging (marked as such in Finished jobs), or you mark the card done, it leaves the board for **View finished jobs** -- so the Review column keeps meaning "needs your review". A finished card stays finished: it is the record of what shipped, and follow-up work is a new job. An agent that stops to ask you something turns its card orange and puts a count on the Jobs tab; click it to land in that terminal, answer, and it carries on. Claude Code asks "do you trust this folder?" the first time it runs anywhere, and every worker gets a brand-new worktree, so the board accepts that for its Claude Code workers: before the spawn it adds the worktree's path to `~/.claude.json` (or `$CLAUDE_CONFIG_DIR/.claude.json`) as trusted. That is one entry, written to a temp file and renamed over it, only when the file already exists and parses, and abandoned if Claude Code writes the file meanwhile. If the dialog shows anyway, it picks "Yes" on the screen: it never presses Enter while "No, exit" is highlighted, and never sends Escape, which exits. The trade-off: a trusted folder loads the repo's own `.claude/settings.json`, so its hooks run as you the moment the job starts, and its `permissions.allow` rules can pre-approve commands that a strict board or card mode (`plan`, `manual`) would otherwise ask about. That is the trust you give a repo by queueing work on it; for a repo whose contents you have not read, set `TRUST_BOARD_WORKTREES=0` in `.env` to keep the dialog. Hand-started agents keep it too, with one exception: codenames are reused, so an agent that later lands on a worktree path a board worker once had finds it already trusted. Claude Code 2.1.282 also counts a repo's main checkout as covering its worktrees, so a repo you have trusted there never shows the dialog either way. Codex asks the same ("Do you trust the contents of this directory?"), and a Codex worker is started with `-c projects={"<worktree>"={trust_level="trusted"}}`, which trusts that one worktree for that run and writes nothing to `~/.codex/config.toml`; a trusted folder lets the repo's Codex project config, hooks and exec policies load, the same trade-off. `TRUST_BOARD_WORKTREES=0` keeps the dialog for both CLIs. An orphan re-spawned onto a card still In progress or in Review (its saved card, or the card on its branch) is that card's board worker again and gets the same trust; one with no card is not, so it asks again.
- **Scheduled jobs** -- A card can also be a schedule, fired by cron (`0 9 * * 1-5`, or `@daily`) in the server's local time. The schedule itself stays in To do; each time it comes due it posts a run card that goes through the board like any job: its agent reports back with `finish_job`, the result waits in Review, and the agent is released at Done. Runs report a summary by default; set **Pull request: Required** on the schedule for runs that should open a PR. A schedule never piles up work: it holds off while its last run is still going or while that run's PR is open (merging or closing the PR files the run away and lets the schedule run again), and a newer summary-only run replaces the last unread one in Review (the older one moves to Finished jobs with its summary, and the newest says how many it replaced). Finished jobs keeps a schedule's newest 50 runs. **Pause** holds further runs without deleting the schedule; **Resume** sets the next run from that moment, so a schedule paused for a week doesn't fire the instant it comes back.
- **Ask an agent to post a job** -- Say "add that to the job board" to an agent you are already working with and it posts the card itself, so noticing work does not mean stopping to type it into the form. The board appears in every Claude Code and Codex agent as an MCP tool, so the agent can see it without being told it exists; under the default permission mode Claude Code still asks you to approve the call, so a card is never filed behind your back. A card an agent files always inherits the board's permission mode -- an agent cannot pick the mode the board will spawn with. It runs on the same CLI as the agent that filed it unless the agent names another; a card a person files runs on Claude Code unless they pick Codex. The card lands in To do showing "via <agent>", and runs in that terminal's repo unless the agent names another. The same agent can read the board back to you and change a card you have not started yet -- "what is queued?", "what does that card say?", "add the repro steps to it". A card that has left To do is closed to edits, for you and for it alike, because its agent already has the text; an agent cannot touch a card someone else queued; and an edit that does land is announced and shown on the card, so a rewritten card never reads as the work of whoever queued it.
- **Agents message each other** -- Say "ask Viper what it changed in jobs.js" and the agent sends the question itself, whether Viper runs on Claude Code or Codex. Every agent has two MCP tools for this, `list_agents` and `send_message`, on the same server as the job board. Claude Code's own messaging only reaches other Claude Code sessions. A message is typed into the other agent's terminal as a new turn, headed with who sent it, so you see it arrive and the agent answers it like anything else you typed. It is typed in only while that agent rests at its prompt: never while it is working, never into a permission or trust dialog the app recognises (the Enter would answer it), and not within 30 seconds of you typing in that terminal. "Rests at its prompt" means no recognised dialog is on screen, so a dialog a new CLI release words differently could still be answered by the Enter. Until then it waits in a queue of up to 20, and the sender gets a message id: while the message is still queued it can take it back with `withdraw_message`, or rewrite it in place with `send_message`'s `replaces`, so a note overtaken by events (a PR since merged) is never acted on. Only the sender can do either, and board notices and approval requests are out of reach. The reply comes back the same way. An agent reaches only agents with the same owner, never a plain shell tab, and one agent can send another at most 10 messages in 10 minutes, so two agents cannot keep answering each other for ever. An agent that never asks before acting (`bypassPermissions`, `--dangerously-skip-permissions`, or on Codex `--yolo`, `danger-full-access`, `--ask-for-approval never`, `--full-auto`, or any `-c`/`--profile` override) only takes messages from another agent that never asks: otherwise any agent could borrow its permissions just by asking it to do something. `AGENT_MESSAGING=open` in `.env` lifts this rule for all your agents; it changes nothing when every agent runs in the same kind of mode, and an agent the rule refuses is told why. This is read off the command line the agent was started with, so a bare `claude` or `codex` whose own config file turns the questions off is not caught by it. Billion is the one exception to both rules: every agent can reach it. A message is a prompt, and it runs with the recipient's permissions, not the sender's: an agent in `bypassPermissions` acts on what it is sent as it would on what you type. The header says the message came from an agent, and the body is quoted line by line so it cannot pass itself off as you. That helps, but it is not a sandbox.
- **Works on a phone** -- Below 700px the three panels become one screen at a time, switched from a Files / Office / Terminal bar at the bottom. Tapping a desk or whiteboard in the office lands you in that terminal or the job board, and opening a file diff lands you in the office panel, the same as on a desktop.
- **Dark/light themes** -- Gold-accented dark theme and a warm low-glare paper light theme tuned for long sessions (see [DESIGN.md](../DESIGN.md)). Toggles instantly, terminal colors and office canvas included.
- **Agents & accounts** -- The gear next to the theme toggle opens a read-only Settings panel listing each agent CLI found on the PATH (Claude Code, Codex, Gemini CLI, opencode, aider and others) with its version and path, and under Claude Code, Codex and Gemini CLI each login folder (the default marked) with its email, plan and logged-in state. Scanned once at start; **Refresh** rescans. It only runs each CLI's local status check and reads the email from its login file, and never returns or logs a token.
- **Live sync** -- Branch names, file changes, line-level diff stats (+/-), and agent states update in real time across all panels.
- **Voice input** -- Dictate prompts instead of typing. Click the mic button floating at the terminal's bottom-right (or `Cmd+D`), allow microphone access on first use, speak, and the transcript is typed into the active terminal; press Enter to send. Uses the browser's Web Speech API (Chrome, Edge, Safari; the recognition language follows your browser's locale) and needs HTTPS or localhost -- for remote access use `tailscale serve` (see [REMOTE.md](REMOTE.md)). The mic is deliberately bounded: it stops after ~1 minute without delivered speech, always after 5 minutes, on switching or closing agents, when an agent's shell ends, when the tab is hidden, and on a phone when you leave the terminal panel. Two things to know: most browsers process speech on vendor servers (Chrome/Edge send audio to Google/Microsoft; Safari may process on-device), so don't dictate secrets; and transcripts arrive as keystrokes, so a program waiting on a single key (a pager, a y/n prompt) reacts to speech like typing -- watch the prompt while dictating. OS-level dictation (macOS dictation, iOS keyboard mic, Windows `Win+H`) also types straight into the terminal and works in any browser. The Billion tab has its own mic beside its text box, with the same limits, that dictates into the box instead of a terminal (`Cmd+D` toggles it while that tab shows); see [BILLION.md](BILLION.md#read-aloud-and-dictation-in-the-tab).
